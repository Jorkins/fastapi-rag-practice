0为什么是这套栈

选型不是追新，而是「每一层都解决一个明确的问题」。

层选型解决什么问题
WebFastAPI原生 async + 自动 OpenAPI 文档 + 依赖注入
配置Pydantic v2类型安全的环境变量解析，启动即校验
ORMSQLAlchemy 2.0 async异步会话，与 FastAPI 事件循环同构
异步任务Celery + Redis文档切分/向量化是重活，必须移出请求线程
定时任务APScheduler + Celery Beat进程内轻量任务与分布式周期任务互补
向量检索numpy → pgvector教学用内存余弦，生产用数据库内 ANN
关键认知：RAG 的「检索质量」取决于切分（chunk）和向量化（embedding）两个前置环节，而不是 LLM。先把检索链路做对，再谈模型。

1架构总览

两条核心链路：写入（索引）和读取（问答）。写入走 Celery 异步，读取走同步 RAG 链路。

写入链路（异步）

上传接口只做「落库 + 入队」，立即返回。Celery Worker 从 Redis 取任务，执行切分 → 向量化 → 写 chunks 表。这样 API 不会被文档解析卡住。

读取链路（同步）

提问接口同步执行：向量化 query → 检索 top_k 切片 → 拼 Prompt → 调 LLM → 返回答案 + 引用来源。

2项目结构分层

分层的核心目的：让变更被限制在单一层内。换 embedding 实现不动路由，换数据库不动 RAG 逻辑。

app/ # 应用包
├── main.py # 入口 + lifespan（启动建表、启调度器）
├── core/ # 横切基础设施
│ ├── config.py # Pydantic Settings 配置
│ ├── db.py # SQLAlchemy async engine/session/Base
│ └── celery_app.py # Celery 实例 + beat_schedule
├── models/ # ORM 模型（Document / Chunk / IndexTask）
├── schemas/ # Pydantic 请求/响应模型
├── api/ # 路由 + 依赖注入
├── rag/ # RAG 五组件（可插拔）
├── services/ # 业务编排（组装 RAG 链路）
├── tasks/ # Celery 异步任务
└── scheduler.py # APScheduler 进程内定时任务
层职责不该做什么
api/参数校验、协议转换、返回响应不该写业务逻辑和 SQL 细节
services/编排多个组件完成一个业务动作不该直接碰 HTTP
rag/单一职责的纯组件不该依赖 FastAPI
models/数据表结构不该含校验/业务规则

3配置管理

用 pydantic-settings 做类型安全配置：环境变量在启动时被解析并校验，写错字段名或类型会立刻报错。

app/core/config.py
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    database_url: str = "sqlite+aiosqlite:///./rag.db"
    celery_task_always_eager: bool = False
    chunk_size: int = 500
    embedding_provider: str = "mock"

@lru_cache
def get_settings() -> Settings:
    return Settings()
实践要点：@lru_cache 保证全局单例；字段名自动映射为大写环境变量（DATABASE_URL → database_url）；测试里用 os.environ 覆盖即可注入不同配置。

4数据库层（SQLAlchemy 2.0 async）

异步引擎与会话工厂是全局单例；每个请求通过依赖注入拿到独立会话。

app/core/db.py
engine = create_async_engine(settings.database_url, future=True)
async_session_factory = async_sessionmaker(engine, expire_on_commit=False)

async def get_db():
    async with async_session_factory() as session:
        yield session   # 请求结束自动关闭

ORM 模型（SQLAlchemy 2.0 声明式）

app/models/document.py
class Document(Base):
    __tablename__ = "documents"
    id: Mapped[str] = mapped_column(String(36), primary_key=True)
    status: Mapped[str] = mapped_column(String(20), index=True)
坑：expire_on_commit=False 是 async 会话的常见做法——commit 后继续访问已加载属性，否则会触发「隐式懒加载」导致 MissingGreenlet 报错。异步环境里所有关系访问都必须显式加载（selectinload 等）。

5RAG 五步链路

把 RAG 拆成五个可替换组件：chunker → embedder → retriever → prompt → llm。每一步都通过抽象基类隔离实现。

5.1 切分 chunker

app/rag/chunker.py
def chunk_text(text, chunk_size=500, overlap=50):
    # 重叠保证跨切片边界的信息不丢失
    ...
为什么 overlap 重要：一句话被硬切在边界处时，前半句在一块的末尾、后半句在下一块的开头，检索时任何一块都可能拿不到完整语义。重叠让边界内容重复出现。

5.2 向量化 embedder

app/rag/embedder.py
class Embedder(ABC):
    @abstractmethod
    async def embed(self, texts) -> list[list[float]]: ...
坑：入库和查询必须用同一个 embedding 模型，否则向量不在同一空间，相似度全部失真。工程里用 get_embedder(provider) 统一工厂避免不一致。

5.3 检索 retriever

app/rag/retriever.py
# 教学：内存全量余弦；生产：pgvector  <=> 运算符库内 ANN
scored.sort(key=lambda x: x[0], reverse=True)
return scored[:top_k]

5.4 Prompt 构造

app/rag/prompt.py
SYSTEM_PROMPT = "只根据提供的上下文回答，不知道就说不知道，不要编造。"
user = f"上下文：\n{block}\n\n问题：{question}"
实践要点：把「只依据上下文 + 标注引用编号」写进 system prompt，是抑制幻觉最便宜有效的手段。

5.5 LLM 调用

抽象基类 + 工厂函数，mock 模式把检索到的上下文回显，证明「检索」环节生效；生产接入 OpenAI 兼容接口（DeepSeek / 通义 / Ollama 都兼容 /v1/chat/completions）。

6异步任务 Celery

文档切分 + 向量化是重活，必须移出请求线程。上传接口只入队，立即返回。

app/tasks/indexing.py
@celery_app.task(name="app.tasks.indexing.index_document")
def index_document(document_id):
    asyncio.run(_index(document_id))  # 包异步逻辑

# 上传接口里：
index_document.delay(doc.id)

幂等任务设计

参考 Mini-RAG Project：任务状态落库到 IndexTask 表，状态机 queued → running → done/failed。异常时回滚并把 document 置为 failed，避免「半索引」脏状态。

本地降级：CELERY_TASK_ALWAYS_EAGER=true 时任务同步执行，无需 Redis 即可开发调试；生产置 false 并启动 worker。

7定时任务：两套互补

维度APSchedulerCelery Beat
运行位置FastAPI 进程内独立 Beat 进程
部署复杂度低高（需 Redis）
分布式否（单机）是
任务持久化需配置内置
适用定时统计/清理/重建索引分布式重活（切分/向量化）
 
app/scheduler.py
# async 环境必须用 AsyncIOScheduler，否则阻塞事件循环
scheduler = AsyncIOScheduler(timezone="Asia/Shanghai")
scheduler.add_job(report_ready_count, "interval", seconds=60)
结论：两者可共存——重活交给 Celery Beat（分布式、可扩容），轻量周期任务留在 APScheduler（进程内、简单）。

8测试
